1. 공통 규약

인증 — 전 API Authorization: Bearer <accessToken> 필요 (예외: POST /auth/login/{provider}·POST /auth/refresh). 로그인은 SSAFY·Google OAuth 인가 코드 방식: 프론트가 code 수신 → 서버로 전달 → 서버가 교환·검증. Access는 본문, Refresh는 httpOnly 쿠키 + Redis 회전 관리 — 재사용 탐지 시 해당 유저 토큰 전체 폐기. 프로바이더 계정과 회원은 1:1(이메일 자동 병합 없음).
지갑 서명 — 온체인 동반 요청 — 토큰이 이동·소각되는 요청 (예측 등록(슬롯 초과) · 구독 결제 · 광고 등록 · 대회 시즌 참가)과 지갑 연동은 본문에 지갑 서명 동반. 서명 알고리즘은 EIP-191 personal_sign(토큰증권 API 4.1.2와 동일)이고, 서명 대상은 JSON이 아니라 줄 구분 문자열이다 — 키 순서·공백·숫자 표현이 다른 JSON 직렬화 차이로 프론트·서버가 서로 다른 바이트를 서명하는 사고를 원천 차단하고, 지갑 팝업에서 사람이 읽을 수 있게 하기 위함. 
antenna:<행위>:v1
<도메인 필드>=<값>      // 금액·대상 등 변조되면 안 되는 값 전부
chainId=<체인 ID>
nonce=<POST /wallet/nonce 로 발급받은 값>
nonce는 요청 본문에 넣지 않는다 — 서버가 userId로 Redis에서 꺼내 본문 필드로 payload를 직접 재조립한다. 클라이언트가 조립한 payload 문자열을 그대로 받으면 "payload에는 A를 적고 처리용 필드에는 B를 넣는" 변조가 가능해지기 때문이다. 재사용 방지는 nonce 1회성(Redis TTL 5분, GETDEL 소비)이 담당하므로 payload에 timestamp를 넣지 않는다. chainId는 반드시 POST /wallet/nonce 응답의 값을 그대로 쓴다 — 지갑에서 eth_chainId로 읽으면 사용자가 고른 네트워크 값이 와서 서버가 조립한 payload와 어긋나고, 그러면 복원 주소가 달라져 원인이 로그에 남지 않는 401이 난다. 서버는 복원 주소를 연동 지갑(users.wallet_address, 소문자 정규화)과 대조, 불일치 시 401 SIGNER_MISMATCH. 미연동이면 400 WALLET_NOT_LINKED. 부인방지 목적.
확정 2026-08-31 (ANT-AUTH-04·06 구현). ERD·유저플로우의 "EIP-712" 표기는 v0.4에서 함께 정정했다. docs/기술아키텍쳐.jpg는 이미지라 수정 불가 — 소유자 확인 필요. 712가 아닌 이유: 컨트랙트가 사용자 서명을 검증하지 않는 구조(릴레이어가 서버 키로 전송)라 712의 이점이 발동하지 않는다.
202 + 작업 리소스 폴링 — 온체인 트랜잭션 동반 요청은 202 Accepted로 접수만 하고, 응답에 operationId와 Location: /api/v1/operations/{operationId}를 담는다. 클라이언트는 리소스별로 다른 조회 API가 아니라 GET /operations/{operationId} 하나를 폴링(3~5초)해 PENDING → SUCCEEDED / FAILED를 확인한다. 전이는 체인 인덱서가 수행하며, 도메인 리소스(구독 ACTIVE·앵커 CONFIRMED·광고 ACTIVE)도 같은 인덱서가 함께 갱신한다. 체인 장애 시 온체인 동반 요청만 실패하고 조회는 정상. 화면 언어: PENDING="블록 확정 대기".
왜 리소스별 폴링이 아닌가 — 202를 쓰는 4곳(예측 슬롯 초과 소각 · 구독 결제 · 광고 등록 · 대회 참가)의 상태값·조회 경로가 전부 달라 프론트가 4가지 폴링 코드를 갖게 된다. 특히 광고는 PENDING을 볼 수 있는 조회 API가 아예 없었다(/ads/active는 ACTIVE만). 작업 리소스로 통일하면 폴링 코드 1개, 실패 사유 스키마 1개이며, 2차에 STOMP로 전환할 때 채널 1개만 열면 된다.
멱등성 — 상태를 만드는 POST에는 Idempotency-Key 헤더(클라이언트 생성 UUID)를 필수로 받는다. 서버는 (userId, endpoint, key)로 최초 응답을 저장(TTL 24h)하고, 같은 키의 재요청에는 처리하지 않고 저장된 응답을 그대로 반환한다.
왜 필요한가 — 이 서비스는 되돌릴 수단이 없다. 예측은 수정·삭제 API가 없고, 토큰은 소각되고, 모의투자 체결은 금융망 출금까지 나간다. 네트워크 타임아웃 후 클라이언트가 한 번만 재시도해도 슬롯 2개 소모 · 토큰 2회 소각 · 이중 체결 · 게임일 2일 전진이 되고 복구 경로가 없다. 배치 계층은 이미 멱등성을 갖췄다(batch_runs.business_date UQ · 날짜 키 upsert · chain_events UQ · fin_api_logs.institution_tx_no UQ) — 비어 있던 건 API 계층뿐이다.
필수 대상 — POST /predictions · /seasons/{id}/orders · /seasons/{id}/join · /channels/{userId}/subscriptions · /ads · /reports · /posts · /uploads. 키 누락 시 400 IDEMPOTENCY_KEY_REQUIRED, 같은 키·다른 본문이면 409 IDEMPOTENCY_KEY_REUSED.
게임일 진행은 예외 — POST /seasons/{id}/advance는 키 대신 본문 expectedDay로 낙관적 잠금을 쓴다(현재 게임일과 다르면 409). 재시도해도 두 번 전진하지 않고, 여러 탭에서 동시에 눌러도 한 번만 나간다.
수정·삭제 불가 원칙 — 예측·근거에는 수정/삭제 API가 존재하지 않는다(append-only). 상태 전이는 판정 배치만 수행한다. 이것이 서비스의 존재 이유다.

본문은 { code, message, field? } 세 필드로 고정한다. 프론트가 code 문자열로 분기하므로 한 번 정한 값은 바꾸지 않는다. field는 입력값 오류일 때만 채우고 그 외에는 키 자체를 생략한다. 검증 실패가 여러 필드에 걸쳐도 첫 번째 위반 한 곳만 내려 화면이 한 번에 한 곳을 가리키게 한다. HTTP 상태 코드는 본문에 넣지 않는다 — 응답 상태와 중복이고, 두 값이 어긋나면 어느 쪽이 참인지 프론트가 판단할 수 없다. 파서·프레임워크가 만든 내부 메시지(타입 이름 등)는 message로 흘려보내지 않고 위 어휘의 고정 문구로 바꿔 내린다.

202 작업 실패는 형식이 다르다 — GET /operations/{operationId} 응답의 error: { code, message }에 담긴다. HTTP 상태는 200이고 status: "FAILED"로 구분한다. code 어휘는 아래 표를 공유한다.

4.2 오퍼레이터 위임 결제 구독 자동 갱신

ERC-1400의 오퍼레이터 = 토큰 보유자가 특정 주소(우리 서비스 지갑)에 "내 토큰을 대신 옮길 권한"을 승인해 두는 표준 개념. 흐름:
① 최초 구독 시 사용자 서명 1회로 결제 + 오퍼레이터 승인 동시 처리(payload에 operatorAuthorize: true).
② 이후 만료 시점마다 갱신 배치(B4)가 사용자 개입 없이 위임 전송으로 현재 구독료를 70:30 두 건 이체 → 인덱서 확정 → +30일 연장.
③ 갱신 전 구독료가 변경돼 있으면 먼저 알림. 해지(DELETE /subscriptions/{id}/renewal) 시 배치가 건너뜀.
④ 잔액 부족·위임 해제로 실패 시 EXPIRED 전이 + 알림.
⚠️ 오퍼레이터 승인/해제의 정확한 토큰증권 엔드포인트는 스펙 확인 필요(여부 조회만 목록에 있음: GET …/roles/operator).

매 영업일 당일 봉인 커밋들의 머클루트 1건 앵커, 실패분은 다음 회차 재시도. salt 리빌은 오프체인 (만기 후 GET /predictions/{id}/proof) — 온체인 루트와 대조해 누구나 재검증.

4.4 이벤트 인덱싱 상시 데몬

Anchored·Transfer(위임 전송 포함)·발행 이벤트를 구독해 chain_events(append-only · UQ tx_hash+log_index)에 기록, 도메인 상태 전이(구독 PENDING→ACTIVE · 앵커 PENDING→CONFIRMED · ledger 기입). 재시작 시 마지막 처리 블록부터 이어 읽기. DB는 온체인 상태의 캐시 — 원천은 체인.
